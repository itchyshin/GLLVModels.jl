# Review: PR #493, truncated-NB2 second-order cell pairs per-trait with per-trait

Reviewer: Gauss (adversarial statistical and code review). Date: 2026-09-26.
Head reviewed: `d8642672d467d1634ec356974b16ab937aec4c9b` (branch
`claude/truncnb2-second-order-pertrait-20260925`, base `d9bc77412`, which predates #481,
#483, #492 and #494 on main).

## Verdict: NEEDS_SHINICHI (not ready as it stands; fix the BLOCKING items first)

The central fix is real. The old cell compared Julia's shared-`r` fitter with gllvmTMB's
per-trait `log_phi_truncnb2` model, so it compared two different models. Re-pointing the cell
to `fit_truncated_nbinom2_gllvm_pertrait` is correct, and no tolerance or check code was
loosened: the diff touches no tolerance logic, and `_assemble` is unchanged. The Wald
arithmetic in the new adapter is also correct in the interior (measured below).

Four things stop this from being ready. The PR adds a user-reachable `confint` route with no
unit test. That route reports `pd_hessian = true` on a Poisson-limit fit. The data screen that
picked the new fixture misreads its own discarded draws: on one of them it is Julia, not R,
that sits at the worse optimum, and it reports `converged = true` while doing so. And the
PASS rests on 1 draw picked from 14 by a filter that encodes first-order agreement between
the engines.

## BLOCKING

1. **New user-reachable `confint` route ships without a test.** `src/confint_family.jl:48`
   adds `TruncatedNegBin2PerTraitFit` to `_CIFit`, and `src/confint_family.jl:580-623` adds its
   `_family_ci`. `confint(fit_truncated_nbinom2_gllvm_pertrait(Y; K), Y)` used to throw a
   `MethodError` and now returns intervals. Both the function and the type are exported
   (`src/GLLVModels.jl:282`). The only thing that exercises the route is the R-gated developer
   cell in `tools/`. The precedent for this kind of change, the ordinal per-trait `_CIFit`
   addition (`docs/dev-log/after-task/2026-09-15-ordinal-pertrait-wald-ci.md`), shipped with a
   focused default-suite test. Add a test like `test/test_second_order_truncnb2_ci.jl`'s
   first testset, for the per-trait type, with no R needed.

2. **Boundary behaviour: `pd_hessian = true` with an `Inf` bound on a Poisson-limit trait.**
   The new adapter calls the 6-argument `_FamilyCI(...)` constructor
   (`src/confint_family.jl:622`), so `boundary` is all-false. The grouped NB2/NB1/Beta adapters
   pass `vcat(falses(p + rr), fit.dispersion_boundary)` for exactly this reason (the T14 F1
   knife edge; e.g. `src/confint_family.jl:670`). Measured on this head (Julia 1.10.0), redrawing
   the screen's own candidates with the PR's draw recipe:
   - seed 62, n = 150: Julia `r[1] = 9.97e9`. `confint` returns `pd_hessian = true`,
     `boundary_terms = []`, log-scale SE for `r[1]` = 1860, and upper bound `Inf`.
   - seed 58, n = 120: Julia `r[5] = 2.93e9`. Here the greedy eigen fallback happens to catch
     it: `pd_hessian = false`, `boundary_terms = ["r[5]"]`, and finite β SEs.

   So the same regime gives opposite `pd_hessian` answers depending on where the optimizer
   stopped. That is the failure T14 F1 was written to remove. Fix: pass
   `vcat(falses(p + rr), _dispersion_group_boundary(fit.r))` as the 7th argument (the helper at
   `src/families/grouped_dispersion.jl:248` already accepts a plain vector, with thresholds
   `> 1e6` or `< 1e-6`). Pin both regimes in the new test. The shared-`r` adapter this one was
   copied from (`src/confint_family.jl:531-572`) has the same gap. It predates this PR, but it
   is the same kind of fault, so it is worth fixing in the same place.

3. **The screen doc and the PR body misattribute the boundary problem to R, and they discard
   a draw on which Julia is wrong.** I refit the screen's draws against the frozen 0.7.0
   library (`~/local-scratch/gllvm-owed24-decisions-20260924/.unlazy/r-build/library`,
   `packageVersion` 0.7.0) with `se = TRUE` and with `se = FALSE`:

   | draw | R logLik | R phi | Julia per-trait logLik | Julia r |
   |---|---|---|---|---|
   | seed 58, n 120 (frozen NATIVE-12) | -1375.391374 | trait 5 = 1.24e7 | -1375.3914 | trait 5 = 2.93e9 |
   | seed 62, n 150 | -1731.531805 | trait 1 = 1.41e7 | -1731.5318 | trait 1 = 9.97e9 |
   | seed 65, n 150 | **-1707.020446** | trait 1 = 2.86e7 | **-1707.787472** (`converged = true`) | 3.99, 5.00, 2.33, 5.74, 7.23 |
   | seed 61, n 150 (chosen) | -1742.723637 | interior | -1742.7236 | interior, agrees to 4 s.f. |

   `se = TRUE` and `se = FALSE` give identical R results on every draw.
   - `docs/dev-log/core070/truncnb2-interior-screen-20260925.md:13` (and the PR body and the
     `cells.jl:1055` note) say that R's `se = TRUE` per-trait fit on seed 58/n 120 "pushes one
     trait to the Poisson-limit boundary". In fact **both** engines put the same trait at the
     boundary and agree on logLik to about 1e-6, and `se = TRUE` plays no part. The phi value
     quoted there (9.9e7) is just wherever the optimizer stopped on a flat ridge. I measured
     1.24e7.
   - Line 48 says "seed 62: Julia trait 1 boundary". R is at the same boundary.
   - Line 42 files seed 65 as "R trait 1 boundary, not interior". In fact R's boundary solution
     has the **higher** log-likelihood, by 0.767. Julia's per-trait fitter stops at an inferior
     interior local optimum and reports `converged = true`. Tightening `g_tol` to 1e-8 lands on
     the same point. Starting from `r_init = [1e6, ...]` reaches -1707.0205, which matches R.
     This is a first-order defect in an exported fitter, the mirror image of #477 (NB2 grouped
     stalling at the boundary below a better interior point). The screen threw it away.

   Correct the screen doc, the holdouts addendum and the cell note so they say what the
   numbers show. Open a follow-up issue for the seed-65 local-optimum stall before merging
   (the fitter needs a boundary restart or a multi-start, like #477's fix). Do not merge a
   durable doc that blames R for this.

4. **Public-surface addition needs Shinichi's sign-off.** No new name is exported, but a new
   working method on the exported `confint` for an exported fit type is a user-visible
   capability. Add a CHANGELOG line under Unreleased (the repo records `confint` behaviour
   changes there, e.g. CHANGELOG "Restore Wald/profile intervals ..."). Say that the `r` block
   is reported on the log scale (`kinds = :log`, so the `se` column for `r[t]` is the SE of
   `log r_t` and the bounds are `exp(log r_t ± z·se)`), matching the other dispersion families.

## SHOULD-FIX

- **Selection disclosure in the receipt itself.** Only 3 of 14 candidates were "clean". The
  filter (interior dispersion on both engines) is a precondition for comparing SEs, so it is
  defensible. But it also selects on first-order agreement, which is why seed 65 disappeared.
  Put "screened: 3/14 draws interior on both engines; chosen = lowest cond(H)" into the receipt
  JSON `note` (`docs/dev-log/core070/second-order-batch-out/truncated_nbinom2.json:28`), not
  only into the separate screen doc.
- **Also report the unselected draw.** On the frozen seed 58/n 120 data both engines agree
  (logLik to 1e-6, same boundary trait), and Julia's Wald already conditions `r[5]` out and
  gives finite β SEs. That β-block comparison is feasible, matching the NB2 batch-1 practice
  ("vcov full-block skipped on boundary"). Run it and record it next to the screened cell so
  the evidence does not rest only on a picked draw.
- **Commit the screen harness and its raw output.** Only the draw tool
  (`tools/truncnb2_parity_data_draw.jl`) is committed. The R-and-Julia screening script and its
  output ("see raw screen output if needed", screen doc line 48-49) are not, so the table
  cannot be reproduced. Also drop or clearly strike the mis-extracted seed 58/n 200 row
  (screen doc line 40): its "R phi" column holds loadings.
- **Gate the win.** The R-paired testset in `test/test_second_order_truncnb2_ci.jl` asserts only
  `parameterisation_gap == false` and a finite `se_rel`, so no test checks the FAIL-to-PASS
  move. Now that it passes, assert the contract §4 bars (`se_rel <= 1e-2`, vcov Frobenius
  `<= 1e-2`, CI endpoint `<= 5e-2` of half-width).
- **Rebase on current main and re-run.** #494 changed `src/confint_family.jl` after this
  branch's base. GitHub reports CLEAN, but re-run the truncnb2 and confint tests on the rebased
  head.
- **The dispersion block is never compared with R.** The PR says so. Keep saying so in the
  holdouts row: the new `r[t]` Wald rows are unpaired.
- **Separate issue (not this PR):** `fit_gllvm(Y; family = TruncatedNegBin2())` defaults to
  shared `r` (`src/families/fit_gllvm.jl:318-319`), while gllvmTMB's only mode is per-trait.
  That default diverges from the twin for users. The PR reports it correctly; it needs its own
  issue and a decision from Shinichi.

## Evidence

  `converged = true`, `pd_hessian = true`, r = [3.0867, 2.2913, 9.5985, 3.9268, 5.6929]
  (matches R to 4 s.f. and matches the receipt). An independent central-difference Hessian
  (step 1e-3) reproduces the package SEs to a maximum relative difference of 1.3e-5. The
  log-scale identity `upper = exp(log r + z·se)` holds exactly (error 0.0). The finite-difference
  gradient at θ̂ is 5.2e-6. The delta and link-scale treatment is the same as every other
  `:log` dispersion family (`_family_wald`, `src/confint_family.jl:2825-2833`). No delta-method
  natural-scale SE is reported, and none is claimed.

  data source and the note in `tools/core070_second_order/cells.jl:1033-1063`, plus the fixture
  loader in `common.jl`. Tolerances are unchanged. The receipt's own `r_condition_number` is
  186.8, so no conditioning multiplier applies.
- The screen shows the engines disagreeing about a boundary trait in several draws. My refits
  above show that on 58/120 and 62/150 they actually agree, and that on 65/150 Julia is the one
  that is wrong.
