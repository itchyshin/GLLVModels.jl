## Adversarial case (`sd = 2.5`, 5x the issue's own loading scale, 3 seeds x 40 sites)

| seed | main loglik | main non-stat/40 | branch loglik | branch non-stat/40 |
|---|---|---|---|---|
| 6001 | -196.42606583 | 2 | -137.55978991 | 0 |
| 6002 | **-186.28801971** | **0 (healthy)** | **-134.51382753** | 0 |
| 6003 | -184.38366121 | 0 | -175.09072204 | 0 |

Seed 6001 is a second, independent confirmation of the fix (bad on main,
clean and improved on branch). Seed 6003 is unchanged (-184.38 vs -175.09 is
noise... actually a genuine ~9-unit shift; see finding below).

**Finding (`healthy_results_change = true`): seed 6002 is a "healthy" main fit
(converged, 0/40 non-stationary) whose loglik nonetheless changes by ~51.8
units on the branch** (-186.288 to -134.514), and seed 6003's healthy fit
shifts by ~9.3 units. Both branch values are themselves fully stationary at
every site (verified), and both are *better* (higher) log-likelihoods, so
these are not garbage values -- they are the outer optimiser landing on a
different, better local optimum of the marginal-likelihood surface. But this
contradicts the plain reading of the PR's own claim that "small/accepted full
steps are bit-identical to the old loop" and the precedent pattern's promise
of "no change where the old search converged": that guarantee holds
per-site-per-final-iterate, not for the fit as a whole, because damping can
still fire at intermediate outer-optimiser iterates even when the final
answer happens to be locally stationary on both kernels. Whether an outer fit
is "healthy" on main tells you nothing about whether its *path* used the
damped branch along the way, so its final answer can still move. This did
not appear anywhere in my 200-site default-scale probe (`sd=0.5`, diffs
1e-11-1e-13), only at 5x the loading scale -- so it is a real but apparently
scale-gated behaviour, not a routine occurrence at realistic settings. The PR
does not mention or test for this; it should.

## Verdict reasoning

The underlying fix is sound: I reproduced the exact defect on main, reproduced
the exact fix on branch using the PR's own fixture, and then independently
stress-tested it on 200 fresh sites plus a 5x-scale adversarial batch with an
ForwardDiff check that shares no code with the package. Zero non-stationary
sites and zero false `-Inf` on branch across all of that. This is real,
verified progress on #501, not a rubber-stamp.

It is not yet mergeable as constituted:
1. The title violates the "Part of #N, never Fixes #N" rule and would risk
   auto-closing #501 (still open) on merge, ahead of the Linux/1.13 CI run the
   PR itself says it hasn't done.
2. CI has not finished (all 9 checks in progress/queued at review time).
3. The PR's verification narrative overstates seed coverage against the
   issue's own correction comment (5 of 7 macOS-flagged seeds never tested;
   seed 2003's still-anomalous path glossed over), and does not mention that
   a "healthy" main fit's final answer can still move substantially (I saw
   ~52 and ~9 loglik units) once loading magnitudes are pushed well past the
   issue's own scale, because damping can fire at intermediate outer
   iterates even when the final iterate is locally stationary on both
   kernels.

None of these are evidence the fix is wrong; they are evidence the PR's own
paperwork and verification claims are ahead of what was actually checked, and
one hard rule violation (title) that must be fixed regardless.
