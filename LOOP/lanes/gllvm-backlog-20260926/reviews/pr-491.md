## Verdict: NEEDS_SHINICHI (fix the BLOCKING items first)

The receipt reproduces exactly. The PASS is genuine for the dataset it describes. The problem
is how the change of intercept is framed. The first run was not a "bug": it was an ordinary
DGP on which **both** engines found the same runaway-loading (Heywood / quasi-separation)
solution. The run was then discarded, and the intercept was re-chosen after the failure and
tried on one seed only. As written, the record reads as tuning-to-pass, even though the
science can be made honest cheaply. I reproduced the discarded run deterministically (below),
so it is not lost.

## BLOCKING

1. **"Data-generating bug" is not justified by the DGP; call it a design choice and record
   the first run.** `tools/core070_realistic_size_cell.jl:58-59` draws `Λ_true = 0.35·randn`
   and a count-scale intercept `log(2 + 3u)` = 0.69 to 1.61. On the logit scale that gives true
   trait prevalence 0.66 to 0.83, with latent SD about 0.5. That is ordinary for real
   presence/absence data, not a malformed DGP. gllvmTMB 0.7.0's own diagnostic on that very fit
   says quasi-complete separation "produces this at ordinary prevalence". The after-task
   (`docs/dev-log/after-task/2026-09-25-realistic-binomial-cell.md:72` and `:85`) calls it "a
   bug in this run's setup" and says the log "was not kept". The PR body calls it "a
   data-generating bug" and does not mention the discarded run at all.

   Reproduction (this review, Julia 1.10.12, frozen gllvmTMB 0.7.0; the reconstruction is
   confirmed by the fingerprint: observed t16 prevalence = 0.814, exactly as the after-task
   reports):

   | data | Julia `fit_binomial_gllvm` | R `gllvmTMB(binomial)` |
   |---|---|---|
   | first attempt (count-scale intercept) | `converged = false`, logLik -5292.804, max row-norm of Λ = 42.5 at t16 (true max 0.83) | `convergence = 0`, `has_sd = TRUE`, logLik -5292.786, warning "runaway trait loading ... t16 prevalence=0.814; max_loading=44.3; relative_loading=120" |
   | receipt (`β_bin = 0.4·randn`, line 184) | `converged = true`, logLik -6744.539486896926 (bit-identical to the receipt) | `convergence = 0`, logLik -6744.53948696 |

   So the discarded run is a real parity observation in the hard regime. The two engines reach
   the same degenerate solution (logLik within 0.018), but they **flag it differently**: R says
   converged and warns, Julia says not converged with no equivalent diagnostic. To make the
   record honest:
   (a) Say in the PR body and the after-task that the first run was discarded and why, and
   remove the word "bug".
   (b) Commit the first run's outcome as a separate, labelled "separated-regime" record: the
   table above, or a re-run log. The data are fully determined by seed 42 and the
   `β_log`/`η` lines already in the script, with `Y = rand(p, n) .< logistic(clamp(η, -8, 8))`
   drawn right after `Z`.
   (c) Justify the new intercept on its own terms, stated as a design rule: second-order
   parity needs an interior MLE, and `N(0, 0.4²)` logit intercepts keep expected prevalence
   near 0.34 to 0.65 (measured on seed 42). Do not justify it as a correction to a mistake.

## SHOULD-FIX

- **Show seed 42 was not picked.** Only one seed was tried under the new intercept. Run a
  small seed panel (for example 5 seeds under each DGP; about 1 min Julia plus 15 s R per fit
  locally at p=20, n=500) and report two things: how often the count-scale intercept separates,
  and whether the zero-centred DGP passes on seeds you did not choose. This turns a post-hoc
  choice into a measured one.
- **CI-endpoint row is marked "PASS (informal)"** (after-task line 100) for a quantity the
  contract defines exactly. From the committed CSVs (`t4-p6-out/binomial_p20_n500_K2_julia_terms.csv`
  against `..._r_fixed.csv`) I get a maximum endpoint delta of 7.28e-6 and a **maximum ratio to
  the half-width of 4.1e-5**, against a bar of 5e-2. That is a formal PASS. State it that way.
- **The A13 binding proposal overreaches** (after-task lines 127-142). A13
  (`covariance/COV-ORD-LATENT-BARE-RSZ`) is a covariance row whose route is BRG/NAT
  (`true-parity-gate-tier-2026-09-05.md:49`). Every T4 receipt is native-only
  (`fit_*_gllvm`, not the formula bridge). Each compares logLik and the β-block SE/vcov, never
  the covariance estimand (Λ Λᵀ). The proposal also says "Five family/shape combinations" but
  lists four families (13 receipts). As written, A13 would be bound to evidence that does not
  test what the row names. Either withdraw the proposal, or restate it as Binomial RSZ evidence
  toward A7 (`BINOMIAL-LOGIT-2SO`) and leave A13 owed until a bridge route with a covariance
  comparison exists.
- **Receipt provenance.** The receipt records `git_head = d9bc77412`
  (`t4-p6-binomial-p20-n500-K2-receipt-2026-09-25.json`, and the launch log `HEAD=`). That
  commit has no binomial branch, because the scripts were copied to Totoro with rsync and not
  committed there. Record the script SHA-256 or the PR head commit in the receipt, so the run
  can be traced to the code that produced it.
- **Link the flag divergence to a follow-up issue.** Under separation, gllvmTMB reports
  `convergence = 0` plus a runaway-loading warning, while Julia reports `converged = false`
  with no diagnostic. This is the same class as #494's two Binomial runaway fits (see the
  orchestrator summary). One issue should cover both.
