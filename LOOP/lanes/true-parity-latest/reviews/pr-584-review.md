## Findings

### F1 (maintainer decision, not a defect in this PR) — the Gaussian `r_random == ["z_B","s_B"]` expectation is stale at P1; it is a real R implementation change, not a model change

Evidence from the read-only gllvmTMB clone: commit `853daf5f0` ("fix: integrate Gaussian cell effects with compatible conditional outputs", 2026-08-30, between P0 and P1) adds `.gllvmTMB_gaussian_diag_B_eligible()` (`R/fit-multi.R:11395` at P1) and changes the random-vector assembly from

```
P0:  if (use_diag_B && !diag_B_all_skipped) random <- c(random, "s_B")
P1:  if (use_diag_B && !diag_B_all_skipped && !integrated_gaussian_diag_B) random <- c(random, "s_B")
```

with the comment "Exact convolution of the ordinary Gaussian cell effect and observation error avoids the small-stabilizer precision in the inner Hessian. This changes neither Psi nor sigma_eps." For an all-Gaussian, all-observed, ML, Laplace, no-AGHQ, no-map default-unique fit — exactly this fixture — the per-trait cell effect `s_B` is integrated in closed form instead of being a Laplace random effect. So `["z_B"]` is expected at P1; the likelihood is unchanged, which is what the 8e-13 agreement shows. The assertion at `test_gaussian_original_required.jl:51` tests an implementation detail of the R tape, not the model. The PR correctly did not edit it.

Suggested resolution (maintainer's call, outside this PR): approve a P1-scoped edit of the structural check to accept `["z_B"]` when the R fit reports `integrated_gaussian_diag_B` (or accept either list), with the commit `853daf5f0` cited; then re-run the Gaussian scope. Until then the two Gaussian cases stay FAIL and row 00 stays partial regardless (its bridge case is unpaid).

### F3 (non-blocking, maintainer decision #2) — carrying the P0 registration is consistent with the rules; one record inconsistency to note

The carry rule in `true-parity-latest/GATES.md` §"The receipt carry rule" governs carrying *receipts* (measurements) across pins; these rows are measured directly at P1 (`measured_against` = P1 sha), so it does not apply. The registration (which harness cell pays which planned case id) is a maintainer classification-level decision from the P0 case map's `evidence.action` ("harness NATIVE-XX receipt registered as binding for the native planned case per maintainer bulk approval"), and the programme says classifications are the maintainer's, so carrying it unchanged and naming it in every affected receipt (`registration:` field, checked against `family-reconciliation-2026-09-01.json` by `check_registration()`) is the right default. Whether the registration should be re-decided at P1 is legitimately the maintainer's call; nothing here pre-empts it.

One inconsistency between the two P0 records, informational: the reconciliation file registers `CORE070-FAMILY-09-IDENTITY/-09-FIXED-SHAPE-NATIVE-MODEL` to `cell-NATIVE-10-STUDENT.toml`, while the P0 case map's `executable_case_ids` for those rows is `CORE070-A6-STUDENTT-FIXED-DF-PAIRED` (the A6 fixture). The PR follows the case map (A6 re-run; `NATIVE-10-STUDENT` not run) and the tool's registration check skips non-runparity ids, so the two records do not collide, but the maintainer's decision #2 should say which one is authoritative for the 09 rows.

### F6 (non-blocking, robustness) — the value sink's tie to its `@test` is by hand, not by construction

`core070_record_values!` takes `rtol`, `atol` and a free-text `test=` string, each copied by hand from the adjacent `@test`. All 24 call sites match today (checked), and the receipt tool copies the string verbatim into `tolerance_rule`, but nothing fails if a future edit changes a `@test` tolerance and not the record (or vice versa): `--check` re-hashes the values file, not the fixture's assertions. Suggested fix (follow-up, not this PR): a kernel test or lint that, for each `core070_record_values!` call, asserts the `test=` string appears verbatim in the same file, or a small macro that takes the `@test` expression once and derives both.
